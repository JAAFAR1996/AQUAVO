## 1. Real Architecture

The repo is a single-package (`package.json` name `aquavo`, pnpm) full-stack TypeScript app deployed to Vercel. Build is orchestrated by `script/build.ts` (vite for client → esbuild bundle for server), output to `dist/public` (client) + `dist/index.js` (server bundle). Vercel serves the SPA and routes `/api/*` through `api/index.ts`.

| Layer | Path | Description |
|-------|------|-------------|
| **Client** | `client/` | React 19 + Vite SPA. `client/src/` has `pages/`, `components/`, `contexts/`, `hooks/`, `lib/`, `data/`, `messages/`, `styles/`. Entry `client/src/main.tsx`, root `App.tsx`, HTML shell `client/index.html`. Routing via Wouter, data via React Query. |
| **Server** | `server/` | Express + Drizzle ORM. Entry `server/index.ts`; routes in `server/routes/` + `server/routes.ts` + `server/system-routes.ts`; business logic in `server/services/`; data access in `server/storage/`; `server/middleware/`, `server/cron/`, `server/mcp/` (MCP server), `server/ws-server.ts` (websockets). DB client `server/db.ts`, env guard `server/env.ts`. |
| **Shared** | `shared/` | Cross-cutting types & data consumed by both client and server. `schema.ts` (Drizzle schema — 85 `pgTable` definitions, source of truth for `drizzle.config.ts`), `accounting.ts`, `products.ts`, `initial-fish-data.ts`, `mock-products.ts`, `social-analytics-types.ts`, plus `shared/__tests__/`. |
| **API (serverless)** | `api/` | Vercel serverless entrypoints. `index.ts` (main handler — `includeFiles: {server/**,shared/**}`), `ssr-meta.ts` (SSR meta/JSON-LD/OG — SEO source of truth per CLAUDE.md), `pdf.ts`, `_html-template.ts` (AUTO-GENERATED by `script/build.ts`; gitignored), `tsconfig.json`. |
| **Migrations** | `migrations/` | Mixed: 7 drizzle-kit-managed migrations (`0000`–`0006`, tracked in `meta/_journal.json` + snapshots) **plus 15 hand-written SQL files** applied manually (see §3). |
| **Ops scripts** | `script/` & `scripts/` | ~90 + ~250 one-off TS/JS/SQL maintenance scripts (seed, fix, import, verify product data). **Both dirs are gitignored** (`.gitignore` lines 82-84) — local-only operational tooling, not part of the deploy. `package.json` references a few: `build.ts`, `final-setup.js`, `check-db.js`. |

Other real runtime dirs: `client/public/`, `public/`, `e2e/` (Playwright), `test/`, `docs/`. Config files in use: `vite.config.ts` (imports `vite-plugin-meta-images.ts`), `vitest.config.ts`+`vitest.setup.ts`, `playwright.config.ts`, `tailwind.config.ts`, `postcss.config.js`, `tsconfig*.json`, `drizzle.config.ts`, `vercel.json`, `components.json`.

## 3. DB Schema vs Migrations — Drift

> **`npm run db:push` is DANGEROUS and must NOT be run** (per MEMORY.md + CLAUDE.md: schema drifted from Neon; apply additive SQL surgically). This report does not recommend running it.

Findings:

| Observation | Evidence |
|-------------|----------|
| Schema is large | `shared/schema.ts` defines **85** `pgTable`s |
| Drizzle journal tracks only 7 migrations | `migrations/meta/_journal.json` entries: `0000_orange_champions` … `0006_add_financially_counted` |
| **15 migrations applied OUTSIDE drizzle's journal** (manual SQL) | `001_add_admin_features.sql`, `002_add_phone_column.sql`, `003_add_settings.sql`, `004_add_loyalty_system.sql`, `005_loyalty_phase1.sql`, `006_loyalty_phase2.sql`, `007_reels_and_publish_tracking.sql`, `add-order-source-column.sql`, `add_gallery_winner_columns.sql`, `add_original_price.sql`, `fix_and_add_customer_profiles.sql`, `run-cost-columns.sql`, `run-finance-audit-tables.sql`, `run-new-tables.sql`, `run-product-costs.sql` |
| Duplicate `0003` prefix | `0003_add_gallery_prizes.sql` AND `0003_tidy_swarm.sql` both exist — only `0003_tidy_swarm` is in the journal. Naming collision is a drift smell. |
| `drizzle.config.ts` `tablesFilter` lists ~75 tables | Narrower than the 85 in schema — push would only diff the filtered set, another reason push is unsafe here. |

**Drift conclusion:** The DB has been evolved through two parallel mechanisms — drizzle-kit (7 migrations) and hand-written SQL (15 files) — so `migrations/` is NOT an authoritative full history of the live Neon schema. Treat `shared/schema.ts` as the code-side intent and Neon as the live truth; reconcile read-only (e.g. Neon MCP `describe_table_schema` / introspection) before any schema change. Continue applying additive SQL surgically.

**Migration files: keep all** — they are historical record / re-runnable surgical SQL. None are safe-to-delete (deleting loses applied-change provenance).
