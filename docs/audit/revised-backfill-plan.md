# Revised Backfill Plan — GUC-Driven Execution Contract (rev. 4)

**Author:** Agent 3 — BackfillPlanAgent (independent, local-only, no Neon writes)
**Supersedes:** the batch-id handling described in `docs/audit/neon-migration-review.md`
rev. 3, invalidated by the findings in `docs/audit/neon-verification-final.md`
§ "MULTI-AGENT VERIFICATION RUN" (rev. 4).

## 1. What broke rev. 3, and why

Production carries triggers on `order_items_relational` that did not exist when the
original backfill was designed:

- `order_items_record_inventory_sale` (AFTER INSERT) — writes `inventory_movements` for
  every inserted row while `settings.inventory_ledger_mode = 'enforce'`. Backfilling the
  73 missing historical lines would create 73 movements the 100 pre-existing rows never
  got (an internally inconsistent ledger) and would drive 7 products' stock negative,
  most likely aborting the whole transaction.
- `order_items_guard_order_detach` (BEFORE DELETE/UPDATE OF order_id) — blocks removal of
  any row belonging to an audited order. All 12 gap orders are audited, so the batch
  rollback as originally written could delete **zero** rows: it would raise on the first
  row and reverse nothing.

A separate **trigger-safety migration** (owned by another agent,
`add_orderitem_backfill_trigger_safety.sql`) introduces narrowly scoped exceptions to
both triggers, gated on session-local GUCs:

- `SET LOCAL aquavo.backfill_batch_id = '<uuid>'` — the inventory-sale trigger suppresses
  movement creation only for rows whose `metadata.backfill.batch_id` equals this value
  AND whose batch row in `orderitem_backfill_batches` is valid/in-progress.
- `SET LOCAL aquavo.backfill_rollback_authorized = 'on'` (together with the batch-id GUC)
  — authorizes the detach-guard trigger to allow deletion of exactly that batch's rows
  during the rollback transaction.

**The problem this plan solves:** the original forward migration generated its batch
UUID *inside* the `DO` block (`gen_random_uuid()` as the primary-key default), after the
insert had already been planned. The inventory-sale trigger fires per inserted row and
can only see a GUC that was set with `SET LOCAL` *before* that `INSERT` statement runs —
so a batch id invented mid-migration can never be the value in the GUC. The batch id had
to move from "generated by the migration" to "generated by the executor and handed to the
migration as a GUC, before any insert."

## 2. What changed vs rev. 3

| Aspect | rev. 3 | rev. 4 (this plan) |
|---|---|---|
| Batch UUID origin | `gen_random_uuid()` inside the migration's `DO` block, via the table's column default | Minted by the **executor**, before the transaction's INSERT, and passed in via `SET LOCAL aquavo.backfill_batch_id` |
| Forward fail-closed condition | none — always attempted | Missing/invalid/reused `aquavo.backfill_batch_id` GUC → `RAISE EXCEPTION` at the very top of STEP 3, before any parsing or locking |
| `orderitem_backfill_batches` insert | `INSERT ... DEFAULT ... RETURNING batch_id INTO v_batch` | `INSERT INTO orderitem_backfill_batches (batch_id, note) VALUES (v_batch, ...)` — batch row exists, with the executor's id, before the line `INSERT` |
| Inventory movements | undefined / would create 73 asymmetric movements and likely abort on negative stock | **Zero**, by construction: the trigger-safety exception recognizes the GUC set before the INSERT and suppresses movement creation for this batch's rows |
| Rollback authorization | batch-id GUC only | **Two** mandatory GUCs: `aquavo.backfill_batch_id` **and** `aquavo.backfill_rollback_authorized = 'on'`; both fail closed independently, checked before any row is touched |
| Rollback vs. detach-guard trigger | undefined — would have raised on every row (0/12 gap orders deletable) | The trigger-safety migration's exception recognizes both GUCs and permits deletion of exactly this batch's rows |
| Reverse rollback ordering | not specified relative to trigger-safety | Backfill rollback now explicitly documented to run **before** the trigger-safety rollback (§5) |
| Reconcile report (`backfill_orderitems_reconcile_report.sql`) | read-only, no GUCs | **unchanged** — it does no writes and needs no batch identity |

No change was made to: the correctness rules (cost NULL/never 0/never fabricated,
line-by-line canonical identity, ambiguity detection, fail-closed on unresolved lines),
the 8 reason codes, the variant-aware identity, or the "never touch app-created rows"
guarantee. Those were already correct against a trigger-free table and remain correct
here — the sequencing found for triggers required a supply-side change only for who owns
the UUID, not for what gets inserted or how missing lines are found.

## 3. New execution contract

### 3.1 Forward backfill — exact statements, in order

```sql
BEGIN;

-- (1) Executor mints a fresh UUID (application code, e.g. crypto.randomUUID()) and
--     sets it BEFORE this file. There is no default and no way to defer this.
SET LOCAL aquavo.backfill_batch_id = '<fresh-uuid>';

-- (2) Optional override, only after owner review of the reconcile report:
-- SET LOCAL aquavo.backfill_allow_unresolved = 'on';

-- (3) The complete file, unmodified, in this same transaction:
\i migrations/backfill_orderitems_from_jsonb.sql

COMMIT;   -- on ANY error: ROLLBACK;
```

Fail-closed behavior (checked in this exact order, before any parsing, before the
`LOCK TABLE`):

1. `aquavo.backfill_batch_id` absent or blank → `RAISE EXCEPTION 'ABORT: no batch id supplied...'`
2. `aquavo.backfill_batch_id` not a valid UUID → `RAISE EXCEPTION 'ABORT: ... is not a valid uuid.'`
3. `aquavo.backfill_batch_id` already present in `orderitem_backfill_batches` → `RAISE EXCEPTION 'ABORT: batch id % already exists ... supply a fresh, never-before-used UUID'`
4. (unchanged) unresolved lines or ambiguous groups without the override → `RAISE EXCEPTION 'ABORT: reconciliation incomplete ...'`

The batch row is inserted with the executor-supplied id (`INSERT INTO
orderitem_backfill_batches (batch_id, note) VALUES (v_batch, ...)`) **before** the
`INSERT INTO order_items_relational`, so the trigger-safety exception — which looks up
this exact `batch_id` in `orderitem_backfill_batches` — is guaranteed to be able to find
a valid, in-progress batch at the moment the inventory-sale trigger fires per inserted
row. Net effect: **zero** inventory movements are created by this migration, for any of
its inserted rows, in any run.

### 3.2 Rollback — exact statements, in order

```sql
BEGIN;

-- Both mandatory, no defaults for either:
SET LOCAL aquavo.backfill_batch_id = '<exact-batch-uuid-from-orderitem_backfill_batches>';
SET LOCAL aquavo.backfill_rollback_authorized = 'on';

-- Optional, child-branch-only:
-- SET LOCAL aquavo.backfill_drop_control_table = 'on';

\i migrations/backfill_orderitems_from_jsonb_rollback.sql

COMMIT;   -- on ANY error: ROLLBACK;
```

Fail-closed behavior, checked in this order, before any row is touched:

1. `aquavo.backfill_batch_id` absent/blank → `RAISE EXCEPTION 'ABORT: no batch id supplied...'`
2. `aquavo.backfill_batch_id` not a valid UUID → `RAISE EXCEPTION 'ABORT: ... is not a valid uuid.'`
3. **NEW:** `aquavo.backfill_rollback_authorized <> 'on'` → `RAISE EXCEPTION 'ABORT: rollback not authorized...'`
4. (unchanged) batch does not exist / never finished / already rolled back → `RAISE EXCEPTION`
5. (unchanged) selected-row count ≠ recorded `rows_inserted`, or any selected row lacks
   backfill provenance → `RAISE EXCEPTION` before any `DELETE`
6. (unchanged) post-`DELETE` count re-verified against the recorded count, inside the
   same transaction, before `COMMIT`

`aquavo.backfill_rollback_authorized` exists specifically because the detach-guard
trigger (`order_items_guard_order_detach`) blocks deletion of any
`order_items_relational` row belonging to an audited order — which is every row this
backfill ever produces. The trigger-safety migration's exception is what permits the
`DELETE` to succeed for exactly this batch's rows when both GUCs are present; requiring
the GUC here too means this file never even attempts a `DELETE` its own analysis knows
the trigger would reject.

**Locked policy — no inventory reversal.** Because the forward backfill created zero
inventory movements (§3.1), the rollback creates zero reversal movements. There is
nothing to reverse. This file does not touch `inventory_movements` at all.

## 4. Five-operation forward sequence

1. `add_order_item_cost_snapshot.sql` — adds the 8 NULL-default cost-snapshot columns +
   5 constraints to `order_items_relational` (additive, no data change).
2. `add_orderitem_backfill_trigger_safety.sql` — introduces the GUC-gated exceptions on
   the inventory-sale AFTER INSERT trigger and the detach-guard BEFORE DELETE trigger.
   **Must precede** operation 3: without it, operation 3's `SET LOCAL
   aquavo.backfill_batch_id` GUC has nothing to suppress against, and the insert would
   create 73 live inventory movements against `enforce` mode.
3. `backfill_orderitems_from_jsonb.sql`, executed per §3.1 with a fresh executor-minted
   batch UUID. Inserts the 73 deterministically-missing lines with NULL/unknown cost,
   zero inventory movements, full audit trail in `orderitem_backfill_batches`.
4. `add_fulfillment_costing.sql` — depends on `order_items_relational` being complete
   (all 173 lines present) so per-order packaging/reshipment costing has full line data
   to work from.
5. `add_fulfillment_hardening.sql` — hardens the fulfillment costing objects added in
   operation 4.

## 5. Six-step reverse rollback sequence, with ordering rationale

1. **Hardening rollback** (`add_fulfillment_hardening_rollback.sql`) — undo the most
   recently added layer first (strict LIFO).
2. **Fulfillment-costing rollback** (`add_fulfillment_costing_rollback.sql`) — removes
   objects that assumed complete line data; must go before the backfill rollback removes
   any of that data.
3. **Explicit-batch backfill rollback** (`backfill_orderitems_from_jsonb_rollback.sql`,
   per §3.2) — deletes exactly the one batch's rows.
4. **Trigger-safety rollback** (`add_orderitem_backfill_trigger_safety_rollback.sql`) —
   removed only **after** step 3, never before. **Why this order is load-bearing:** the
   trigger-safety migration's exception is the *only* thing that allows step 3's `DELETE`
   to pass the detach-guard trigger for these audited-order rows. If the trigger-safety
   rollback ran first, it would remove that exception, and the backfilled rows — which
   belong to audited orders like every other row in the table — would become permanently
   undeletable by the ordinary rollback path (the same "0 of 12 deletable" failure mode
   the rev. 4 verification run discovered). The exception must outlive the rows it exists
   to let you delete.
5. **Snapshot rollback** (`add_order_item_cost_snapshot_rollback.sql`) — removes the 8
   cost-snapshot columns/5 constraints only after no backfilled row (which populates
   those columns with NULL/'unknown') remains dependent on the trigger-safety exception;
   by this point step 3 has already run, so this is purely schema cleanup.
6. **Optional: disposable-branch audit-table cleanup** — on a disposable rollback-test
   branch only, `SET LOCAL aquavo.backfill_drop_control_table = 'on';` during step 3 (or
   a standalone `DROP TABLE orderitem_backfill_batches;` afterward, once no active batch
   remains) returns the schema byte-for-byte to its pre-backfill object set. On
   production this step is skipped by design — MODE B retains
   `orderitem_backfill_batches` as the permanent audit trail, and a production rollback
   is described as "complete except for the retained audit table," never as an
   unqualified full rollback.

## 6. Files changed and why

- `migrations/backfill_orderitems_from_jsonb.sql` — batch UUID now sourced from the
  mandatory `aquavo.backfill_batch_id` GUC instead of `gen_random_uuid()`; new fail-closed
  guard (absent/invalid/reused GUC) at the top of STEP 3, before locking or parsing;
  `orderitem_backfill_batches` insert now supplies the id explicitly instead of using
  `RETURNING`; header comments document the new hard dependency on the trigger-safety
  migration and the GUC contract.
- `migrations/backfill_orderitems_from_jsonb_rollback.sql` — new mandatory
  `aquavo.backfill_rollback_authorized = 'on'` GUC, checked immediately after the batch-id
  validation and before any query against `order_items_relational`; header comments
  document the two-GUC requirement, the "zero inventory reversal" locked policy, and the
  exact reverse-rollback position relative to the trigger-safety and fulfillment
  migrations.
- `migrations/backfill_orderitems_reconcile_report.sql` — **unchanged**. It is read-only
  and does not participate in the GUC contract.
- `server/__tests__/orderitem-backfill-migration.test.ts` — added
  `runBackfill()`/updated `rollbackBatch()` helpers that supply the new mandatory GUCs;
  every prior call site that invoked the forward migration or rollback now goes through
  these helpers; added two new fail-closed assertions (missing batch-id GUC, missing
  authorization GUC on an otherwise-valid rollback) plus one for a malformed batch-id GUC.
  All prior assertions (fixture fidelity, snapshot guard, byte-for-byte preservation of
  the 100 original rows, idempotency, variant-aware partial top-up, both rollback modes)
  are unchanged in substance.
- `server/__tests__/orderitem-backfill-validation.test.ts` — replaced the single `ALLOW`
  constant with `withBatch()` / `withAllow()` / `withRollback()` helpers that mint a fresh
  UUID per call (each fixture case runs the migration in its own throwaway PGlite
  instance, so id reuse is never actually possible, but the helpers keep every call site
  honest about the new required GUC); added two new fail-closed tests for rollback
  without the batch-id GUC and without the authorization GUC. All invalid-line-category
  fixtures, the ambiguity fixtures, the variant-identity fixtures, and both rollback-mode
  fixtures are otherwise unchanged.

The PGlite fixtures in both files deliberately do **not** simulate the inventory-sale or
detach-guard triggers (that verification belongs to the trigger-safety migration's own
owner, per this task's scope). What they do verify is that the backfill and rollback
migrations correctly *fail closed* without the GUCs the trigger-safety contract requires,
and correctly proceed once a valid, fresh batch id (and, for rollback, the authorization
flag) is supplied — i.e., that this migration pair holds up its side of the contract
regardless of what the trigger side does.
